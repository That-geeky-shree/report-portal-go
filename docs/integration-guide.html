ReportPortal Go Integration
Developer Guide

Integrating the Go Ginkgo BDD framework with ReportPortal for true real-time test reporting. This end-to-end guide covers everything from the HTTP wire protocol to live UI results, showing you how to stream individual spec results the exact moment they finish, with zero batching and no waiting for the full suite to complete.

Authored by Shriya Pandey · Software Engineer · ReportPortal Go Contributor

00 What is this?

Two Go modules that connect your Ginkgo test suite to ReportPortal with zero test-code boilerplate.

The two modules

ModuleWhat it does
client-go A typed, zero-reflection HTTP client for the ReportPortal v5 REST API. Handles auth, request/response structs, and all raw API calls — create launch, start/finish items, post logs, upload attachments. Use this directly if you want to talk to the RP API from any Go code.
agent-go-ginkgo A Ginkgo v2 reporter that hooks into Ginkgo's lifecycle and uses client-go to stream test results to RP in real time. Includes the ginkgo-rp wrapper binary that manages the launch lifecycle. A single blank import in your suite file wires everything up — no other test-code changes needed.

The open-source test management platform that stores, aggregates, and visualizes test results. This integration speaks its REST API directly over HTTP/JSON + multipart.

01 System Architecture

How all the pieces connect — from your terminal to the ReportPortal UI.

ℹ️
Two-process design: ginkgo-rp (the wrapper) runs in one process and owns the launch lifecycle. ginkgo (the worker) runs as a child process and owns test execution. They communicate through JSON/NDJSON files in $TMPDIR — the wrapper never blocks on test I/O, and parallel workers never fight over a shared socket or lock file.

02 client-go — The HTTP Client

A typed, zero-reflection REST client for the ReportPortal v5 API. No frameworks, no code generation — just resty + typed structs.

Package layout

📄 client.go

All HTTP methods: StartLaunch, FinishLaunch, StartTest, StartChildTest, FinishTest, SaveLog, SaveLogMultipart, StopLaunch, MergeLaunches.

📄 model_reporting.go

Request/response structs: StartLaunchRQ, FinishExecutionRQ, StartTestRQ, SaveLogRQ, Attribute, Timestamp.

📄 model_filter.go

Filter, sort, and paginated list response types for querying launches, items, and filters from the RP API.

📄 model_common.go

Enum constants: Statuses, TestItemTypes, LaunchModes. Type aliases for Status, TestItemType, LaunchMode.

Creating a client

import "github.com/reportportal/client-go/pkg/gorp"

client := gorp.NewClient(
    "https://reportportal.example.com",  // RP server URL — trailing slash and /api suffix are stripped automatically
    "my_project",                          // project name (case-sensitive)
    "user_abc123xyz...",                    // API key from Profile page
)
// HTTP debug output goes to rp-agent.log via the interceptor (never to stdout).
// The Authorization header is automatically redacted in all log output.
// SetDebug(true) is a no-op on the raw client — set rp.debug=true in reportportal.properties instead.
⚠️
30-second timeout: The client sets a 30 s request timeout by default. A stalled RP server will return an error after 30 s rather than hanging the test process indefinitely. Zero-value timeout (hang forever) is not supported.

Key data types

StartLaunchRQ

type StartLaunchRQ struct {
    StartRQ              // Name, Description, Attributes, StartTime
    Mode    LaunchMode   // "DEFAULT" or "DEBUG"
    Rerun   bool         // true = rerun of a previous launch
    RerunOf *uuid.UUID   // UUID of the original launch to rerun
}

// Attribute for launch tagging
type Attribute struct {
    Key    string // tag key (e.g. "build", "env")
    Value  string // tag value (e.g. "1.5.0", "staging")
    System bool   // true = system attribute (shown with lock icon in UI)
}

Timestamp — always epoch milliseconds

// ✅ Correct — ReportPortal v5 requires epoch ms for all time fields
startTime := gorp.NewTimestamp(time.Now())
// Marshals as: 1790967700412  (milliseconds since Unix epoch)

// ✅ A zero Timestamp marshals as JSON null — safe for optional end-time fields
// ✅ Unmarshal handles null, epoch ms, RFC3339Nano, RFC3339, and the RP datetime format
// ✅ JSON field names are camelCase — matching RP v5 API
// StartTime → "startTime"    EndTime → "endTime"
⚠️
API versioning matters: Launch creation uses /api/v1/. All test item and log operations use /api/v2/. The client handles this automatically — do not set the base URL to include /api/v1 or /api/v2. Trailing slashes on the host are stripped automatically.

Error handling

HTTP 4xx responses (bad key, wrong project) are surfaced as errors immediately — they indicate a permanent client error that retrying would not fix. Network errors and 5xx responses propagate as Go errors to the caller; the agent logs them and continues rather than aborting the test run.

03 agent-go-ginkgo — The Reporter

A Ginkgo v2 reporter that hooks into the test lifecycle and streams results to ReportPortal in real time.

Package layout

🔌 reporting_node.go

The init() function that activates when RP_SESSION_ID is set. Stays dormant (warn, not fatal) if the state file is missing. Registers ReportBeforeEach, ReportAfterEach, and ReportAfterSuite hooks. Containers (Describe/Context) are not finished per-spec — they are closed by the wrapper in Phase 3.

🎯 ginkgo_helpers.go

Builds the Describe→Context→It hierarchy in RP. On error, falls back to the parent ID rather than calling log.Fatalf — a reporting failure never kills the test run.

📡 test_listener.go

Wraps client-go with idempotent POSTs — each start call generates a stable UUID so duplicate network calls don't create duplicate RP items. All five Ginkgo failure states (failed, panicked, interrupted, aborted, timedout) map correctly to RP statuses.

🏷 label_helpers.go

Public API: Priority(), TestReference(), Log(). Leaf-node labels take precedence over container labels for priority. TestReference("") returns a safe no-op label instead of an empty string (which Ginkgo rejects).

⚙️ launch_coordinator.go

Two-tier container cache. L2 uses a shared lock file (no PID in name) so competing workers actually contend. O_EXCL + tmp + atomic rename. API key is not stored in the state file — workers re-read it from reportportal.properties to avoid a plaintext credential in $TMPDIR.

📎 attachment.go

AddAttachment(filePath, message) — copies file to a temp dir, queues as a JSON-encoded report entry (not #-delimited), streams to RP as multipart after the spec finishes. CleanupAttachments() is called automatically by ReportAfterSuite.

How the init() hook works

// In pkg/rpagent/reporting_node.go — fires automatically on import
func init() {
    sessionID := os.Getenv("RP_SESSION_ID")
    if sessionID == "" {
        return  // not running under ginkgo-rp — completely dormant
    }

    // Load launch ID, endpoint, project from shared state file (no API key stored there)
    agentState, err := coordinator.LoadAgentState()
    if err != nil {
        log.Printf("WARNING: rpagent: state file not found (%v) — reporting disabled", err)
        return  // graceful degradation: --dry-run or compile errors
    }

    // API key is re-read from reportportal.properties, not from state file
    rpConfig, _ := config.LoadRPConfig()
    globalClient  = gorp.NewClient(agentState.Endpoint, agentState.Project, rpConfig.APIKey)
    globalListener = NewTestListener(globalClient, agentState.LaunchID, agentState.LaunchName)

    // Resolve symlinks so suite cache key matches wrapper (macOS /tmp → /private/tmp)
    suitePath, _ := filepath.EvalSymlinks(suiteFilePath)
    suiteID = agentState.SuiteIDs[suitePath]

    // Register Ginkgo hooks — these fire for every spec in this worker
    ReportBeforeEach(func(spec types.SpecReport) {
        ids := startSpecHierarchy(spec, suiteID)
        activeHierarchies.Store(spec.FullText(), ids)
    })
    ReportAfterEach(func(spec types.SpecReport) {
        // Finishes It/By items only — containers are closed by the wrapper in Phase 3
        finishSpecHierarchy(spec)
    })
    ReportAfterSuite("", func(report types.Report) {
        writeNDJSON(report, sessionID)  // emit per-spec result lines
        CleanupAttachments()            // remove temp copies from $TMPDIR
        writeDoneFlag(sessionID)        // signal Phase 3 this worker is finished
    })
}
💡
Zero test-code invasion: The init() function activates only when RP_SESSION_ID is set by ginkgo-rp. When you run go test ./... normally, the agent is completely dormant — no RP connection is made.

04 Why ginkgo-rp instead of ginkgo?

The single most common question — answered with diagrams and the full end-to-end flow.

The core problem: Ginkgo only covers Phase 2

Every test reporting system needs three distinct phases:

  • Phase 1 — Before tests run: create the launch and suite items in ReportPortal, write a shared state file to $TMPDIR, then hand off to Ginkgo.
  • Phase 2 — While tests run: report each Describe/It/By item to ReportPortal in real time as specs execute inside Ginkgo worker processes.
  • Phase 3 — After all tests finish: read the per-worker NDJSON result files, aggregate stats, finish all suite items, and finalize the launch with a pass/fail status.

Ginkgo's plugin API — ReportBeforeEach / ReportAfterEach — fires exclusively inside the worker process during Phase 2. There is no lifecycle hook that runs before the first test or after the last one. Phases 1 and 3 simply do not exist in plain Ginkgo — which is why ginkgo-rp exists.

Why not just use BeforeSuite / AfterSuite?

A natural first instinct. Ginkgo v2 has SynchronizedBeforeSuite (runs setup once on process 1 in parallel) and ReportAfterSuite (fires once per package). But both are scoped to a single package — there is no cross-suite hook. That leaves two problems unsolvable with suite hooks alone:

The solution: ginkgo-rp as the outer orchestrator

ginkgo-rp lives outside Ginkgo entirely. It spawns ginkgo as a child process and coordinates the full launch lifecycle.

⚠️
Always use --keep-going for multi-suite runs. Without it, ginkgo stops after the first suite failure and workers for later suites never start — so those suites appear missing in RP rather than failed. --keep-going tells ginkgo to continue executing all remaining suites and let ginkgo-rp aggregate the final status correctly. 
ginkgo-rp suite1/ suite2/ suite3/ --keep-going

How $TMPDIR IPC works

Workers and the wrapper never share a socket, pipe, or lock file. All coordination uses plain files in $TMPDIR — safe across any number of parallel processes on the same machine.

📄 rp_agent_state_{sid}.json

Written once by the wrapper in Phase 1. Contains endpoint, project, launch ID, session ID, and suite path → ID mapping. No API key — workers re-read it from reportportal.properties to avoid a plaintext credential in $TMPDIR. Permissions: 0600.

📄 rp_status_{sid}_{pid}.json

One file per worker PID. Each spec appends one JSON line (NDJSON) after it finishes. The wrapper reads all files in Phase 3 to build the aggregate stats.

🚩 rp_done_{sid}_{pid}.flag

Empty file created by ReportAfterSuite when a worker finishes all its specs. Because cmd.Run() is blocking — the wrapper only returns after the entire ginkgo child process exits — all workers are already dead by the time Phase 3 starts. The wrapper waits up to 5 seconds purely as a defensive OS-flush buffer, then proceeds with whatever NDJSON data is present. If no flags are found it logs a warning (likely a compile error or worker crash) and continues.

The L2 container cache

When ginkgo -p runs multiple workers in parallel, each worker processes different specs — but may share the same Describe or Context container. Without deduplication, each worker would POST a separate RP item for the same container, creating duplicates in the UI.

L1 cache — sync.Map in each worker process (in-memory, zero latency). Hit rate is high because a worker processes many specs under the same Describe block.

L2 cache — content-addressable files in $TMPDIR/rp_cache_{sha256_of_key}. Workers compete via a shared lock file (cacheFilePath + ".lock" — no PID in the name). The winner opens it with O_EXCL, writes to a .tmp file, syncs, renames atomically to the final path, then removes the lock. Losers wait and read the completed file.

// launch_coordinator.go — shared lock file + O_EXCL + atomic rename
lockPath := cacheFilePath + ".lock"  // shared name — all workers contend on the same path
lock, err := os.OpenFile(lockPath, os.O_RDWR|os.O_CREATE|os.O_EXCL, 0600)
if os.IsExist(err) {
    // lost the race — wait for the winner to produce the final file
    return waitForFileWithRetry(cacheFilePath, 20, 100*time.Millisecond)
}
defer func() { lock.Close(); os.Remove(lockPath) }()

tmpPath := cacheFilePath + ".tmp"
id := createFunc()              // POST to RP — only the lock holder calls it
os.WriteFile(tmpPath, []byte(id), 0600)
os.Rename(tmpPath, cacheFilePath) // atomic — readers see a complete file

The RP_SESSION_ID dormancy mechanism

// pkg/rpagent/reporting_node.go — fires instantly on worker start
func init() {
    if os.Getenv("RP_SESSION_ID") == "" {
        return  // "go test ./..." or plain "ginkgo" — completely dormant
    }
    // Loads endpoint, project, launch ID — but NOT the API key
    agentState, err := coordinator.LoadAgentState()
    if err != nil {
        log.Printf("WARNING: rpagent init: %v — reporting disabled", err)
        return
    }
    // API key is re-read from reportportal.properties (not stored in $TMPDIR/state.json)
    rpConfig, _ := config.LoadRPConfig()
    globalClient   = gorp.NewClient(agentState.Endpoint, agentState.Project, rpConfig.APIKey)
    globalListener = NewTestListener(globalClient, agentState.LaunchID, agentState.LaunchName)
    ReportBeforeEach(func(spec) { startSpecHierarchy(spec) })
    ReportAfterEach(func(spec)  { finishSpecHierarchy(spec) })  // It/By only; containers done in Phase 3
    ReportAfterSuite("", func(r) { writeNDJSON(r); CleanupAttachments(); writeDoneFlag() })
}
ℹ️
Same pattern across all ReportPortal agents. The Java agent wraps JUnit, the Python agent wraps pytest, the .NET agent wraps the test runner. ginkgo-rp is Go's version — a thin outer binary that owns the launch lifecycle while the plugin inside the runner streams results in real time.

05 Quick Start

From zero to a live launch in ReportPortal.

  1. Install the ginkgo-rp binary 
    go install github.com/reportportal/agent-go-ginkgo/cmd/ginkgo-rp@latest
  2. Add the agent to your test module 
    go get github.com/reportportal/agent-go-ginkgo@latest
  3. Add a blank import in your Ginkgo suite file 
    // mypackage_suite_test.go
package mypackage_test

import (
    "testing"
    . "github.com/onsi/ginkgo/v2"
    . "github.com/onsi/gomega"
    _ "github.com/reportportal/agent-go-ginkgo/pkg/rpagent"  // ← this line only
)

func TestMyPackage(t *testing.T) {
    RegisterFailHandler(Fail)
    RunSpecs(t, "My Package Suite")
}
  4. Create reportportal.properties alongside your go.mod 
    rp.endpoint = https://reportportal.example.com
rp.api.key  = your_api_key_here
rp.project  = my_project
rp.launch   = my-service-tests
rp.debug    = false
  5. Run your tests 
    # replaces: ginkgo ./...
ginkgo-rp ./...
  6. Open ReportPortal and see your results

    Navigate to your project's Launches list. Your launch appears with full Suite → Describe → It hierarchy, pass/fail counts, logs, and attachments.

07 Feature Reference

Every capability the agent exposes, with usage examples.

🎯 Test Priorities (P0–P4)

Tag any test with a priority level using a Ginkgo label. The agent sends priority both as a dedicated field and as an attribute tag (priority: P0) so it is visible on each test item in the RP UI. Priorities also roll up to the launch-level summary and are available as filters.

💡
Leaf labels take precedence. When a Describe container and an It block both carry a rp.priority: label, the agent reads the It block's label first (spec.LeafNodeLabels) and falls back to the full label set only if the leaf carries none. This means you can set a default priority on a Describe block and override it on individual tests without any conflict.
import rpagent "github.com/reportportal/agent-go-ginkgo/pkg/rpagent"

It("critical path — login",   Label(rpagent.Priority(0)), func() { ... })  // P0 — must never fail
It("search results",             Label(rpagent.Priority(1)), func() { ... })  // P1 — high importance
It("UI corner case",             Label(rpagent.Priority(2)), func() { ... })  // P2 — medium
It("edge case — empty input",    Label(rpagent.Priority(3)), func() { ... })  // P3 — low
It("cosmetic — tooltip text",    Label(rpagent.Priority(4)), func() { ... })  // P4 — lowest

🔗 Test Case Linking (TestReference)

Link a test to an external ticket ID (Jira, TestRail, etc.). The agent sends the ID both as a dedicated testReferenceId field and as an attribute tag (testReferenceId: CART-TC-042) so it is visible on the test item in the RP UI — just like priority.

💡
Safe empty and special characters. TestReference("") returns the placeholder label rp.ref:unset instead of an empty string — Ginkgo rejects empty labels. Characters that Ginkgo parses specially (& | ! , ( ) /) are automatically replaced with _ in the label, so reference IDs like CART/TC-042 or T&R-7 are safe to pass directly.
It("user can checkout",
    Label(rpagent.Priority(0), rpagent.TestReference("CART-TC-042")),
    func() {
        // RP item shows attributes: priority=P0 · testReferenceId=CART-TC-042
    })

📝 Structured Logs

Send structured log entries to the current test item in RP. Each call maps directly to a POST /log request — logs appear in the item's ALL LOGS tab in the RP UI, colour-coded by severity.

rpagent.Log("DEBUG", "entering setup phase")
rpagent.Log("INFO",  "request payload: " + payload)
rpagent.Log("WARN",  "response slow — 4.2 s")
rpagent.Log("ERROR", "unexpected status: " + strconv.Itoa(statusCode))
rpagent.Log("FATAL", "database connection pool exhausted")

ℹ️
How logs reach RP — and why they must be called inside an It block.

rpagent.Log() uses Ginkgo's AddReportEntry internally to queue the message. Ginkgo flushes report entries into the SpecReport only after the spec body completes — the agent's ReportAfterEach hook then reads them and sends each one as a POST /log to RP. This means logs called outside a running spec (e.g. in BeforeSuite) are silently dropped.

FATAL does not crash the process. In Go, log.Fatal calls os.Exit(1). rpagent.Log("FATAL", ...) does not — it sends a log entry with severity FATAL to RP and returns normally. The test continues and passes or fails on its own assertions. Use FATAL to flag catastrophic events in your test narrative without aborting the spec.

🪜 By() Step Grouping

Use Ginkgo's built-in By() to create named sub-steps inside a test. Each By() call becomes a child STEP item in RP.

It("completes purchase flow", Label(rpagent.Priority(0)), func() {
    By("adding item to cart")
    cart.Add(item)
    Expect(cart.Count()).To(Equal(1))

    By("applying discount code")
    cart.ApplyCode("SAVE10")
    Expect(cart.Discount()).To(BeNumerically(">", 0))

    By("completing payment")
    result := checkout.Process(cart)
    Expect(result.Success).To(BeTrue())
})
ℹ️
How log routing to By() steps works internally.

Every event (By call, log entry, attachment) recorded during a spec is stamped with a TimelineLocation.Order — a monotonically increasing integer that Ginkgo increments for each event in the spec. When ReportAfterEach fires, the agent reads the completed SpecReport and walks two ordered lists: SpecEvents (contains the By() calls as SpecEventByStart entries) and ReportEntries (contains the logs and attachments). For each log it picks the By() step whose Order is the highest value still ≤ the log's Order — that is the By() step the log was emitted under. Logs before any By() fall back to the It item.

Note: TimelineLocation.Offset (the GinkgoWriter byte position) is always 0 when tests do not write to GinkgoWriter directly. The correct field for ordering is Order, not Offset.

📎 File Attachments

Attach any file (screenshot, HAR, JSON dump, CSV, log) to the current It block. The file path must exist on disk — pass an absolute path or create a temp file. The agent copies it, queues it via Ginkgo's report entry, then streams it to RP as a multipart upload after the spec finishes.

// Signature: AddAttachment(filePath string, description string)
// filePath   — absolute or relative path to the file on disk
// description — label shown in RP next to the attachment

It("dashboard renders correctly", func() {
    screenshotPath := browser.Screenshot() // returns path like "/tmp/shot_123.png"
    rpagent.AddAttachment(screenshotPath, "Dashboard screenshot")
    Expect(page.Title()).To(Equal("Dashboard"))
})

// Creating a temp file inline is the most common pattern:
It("returns correct API response", func() {
    payload := `{"status":"ok","items":42}`
    f, _ := os.CreateTemp("", "response-*.json")
    defer os.Remove(f.Name())
    fmt.Fprint(f, payload)
    f.Close()

    rpagent.AddAttachment(f.Name(), "API response JSON")
    Expect(payload).To(ContainSubstring(`"items":42`))
})
💡
Any It block, any file type. You can call AddAttachment multiple times in one spec — each produces a separate attachment in RP. Maximum file size is 10 MB. Content type is auto-detected from the first 512 bytes, so .png, .json, .csv, .txt, .log, and .html all render correctly in the RP UI. Describe/Context blocks have no spec body, so AddAttachment must always be inside an It.

📊 Parameterized / Table-Driven Tests

Use Ginkgo's DescribeTable + Entry for data-driven tests. The agent automatically detects table entries and extracts parameters from the entry description string — no extra code needed.

ℹ️
Detection rule. A spec is treated as a table entry if its leaf node text contains = and at least one ' or ". Parameters are then extracted by the pattern (\w+)=['"]([^'"]*?)['"]. Entry descriptions that do not follow this format still run and report normally — they just carry no RP parameters. 
DescribeTable("HTTP status handling",
    func(code int, msg string) {
        Expect(handler.MessageFor(code)).To(Equal(msg))
    },
    // ✅ key='value' format → parameters shown in RP test item
    Entry("code='200' msg='OK'",              200, "OK"),
    Entry("code='404' msg='Not Found'",       404, "Not Found"),
    Entry("code='500' msg='Server Error'",    500, "Server Error"),
    // ❌ no key='value' → no parameters (test still runs and reports normally)
    Entry("server error case",               500, "Server Error"),
)

// Combine with priority — labels work the same as on It() blocks
Entry("code='200' msg='OK'", Label(rpagent.Priority(1)), 200, "OK")
💡
Parameters appear in the RP test item detail pane under a "Parameters" section — each key=value pair as its own row. The entry description is also used as the RP item name, so make it human-readable: "code='404' msg='Not Found'" reads better than "404 not found" (which carries no parameters).

⏭ Skip / Pending Tests

All Ginkgo skip mechanisms are correctly reported as SKIPPED in RP.

It("feature not ready", func() {
    Skip("payment gateway not configured in this environment")
})

PIt("pending — needs design review", func() { ... })

XIt("excluded temporarily", func() { ... })

Describe() / Context()TEST✅ trueCreated lazily when the first spec that belongs to it runs. Deduplicated across parallel workers via the L2 file cache (O_EXCL + rename).
It() / DescribeTable EntrySTEP✅ trueThe leaf test node. Carries priority, testReferenceId, parameters, failure log, attachments.
By("...")STEP (child)❌ falseChild of the It step. Created after the spec runs (events read from SpecReport). Logs are routed to the correct By() step by timeline order. hasStats=false prevents double-counting in launch totals.
💡
Why does hasStats matter? ReportPortal propagates pass/fail counts upward — Suite totals come from TEST totals, which come from STEP totals. By() child steps use hasStats=false so they don't get counted in addition to their parent It step. Every other item uses hasStats=true so the rollup reaches the launch-level dashboard correctly.

10 Parallel Execution with -p

Run all test specs across multiple CPU cores simultaneously — ginkgo-rp coordinates the full RP lifecycle automatically.

💡
-p just works. Every flag you pass to ginkgo-rp is forwarded verbatim to ginkgo. No extra configuration needed for parallel execution — the agent handles deduplication and coordination internally.

Commands

# Auto-detect CPU count (recommended)
ginkgo-rp -r -p --keep-going

# Pin to a specific number of workers
ginkgo-rp -r --procs 4 --keep-going

# Parallel + verbose output
ginkgo-rp -r -p --keep-going -v

# Parallel + focus filter
ginkgo-rp -r -p --focus "Authentication"

What happens under the hood

How container deduplication works

When Workers 1 and 2 both encounter Describe("Calculator"), they both try to create it in RP — but only one should win. The L2 cache uses a shared lock file with O_EXCL:

// L1: in-process sync.Map — instant within a single worker
if id, ok := inMemoryCache.Load(key); ok {
    return id.(string)
}

// L2: shared lock file (no PID in name) — all workers contend on the same path
lockPath := cacheFile + ".lock"
lock, err := os.OpenFile(lockPath, os.O_CREATE|os.O_EXCL|os.O_WRONLY, 0600)
if os.IsExist(err) {
    // lost the race — wait for winner to produce the final file
    return waitAndReadID(cacheFile)
}
defer func() { lock.Close(); os.Remove(lockPath) }()

// won — create RP item, write to .tmp, atomically rename
id := client.StartChildTest(parentID, rq)
os.WriteFile(cacheFile+".tmp", []byte(id), 0600)
os.Rename(cacheFile+".tmp", cacheFile)
ℹ️
Shared lock, not per-PID. The lock file has no PID in its name so all workers actually contend on the same path — the winner holds O_EXCL, creates the RP item, writes to .tmp, atomically renames to the final cache path, then removes the lock. Losers wait and read the complete file. Tune wait behaviour with RP_LOCK_RETRY_COUNT and RP_LOCK_RETRY_SLEEP_MS.

Verified parallel behaviour

ScenarioResult
N workers encounter the same Describe blockExactly 1 RP item created — all others read the same ID
N workers each run different specsAll spec results stream to RP in real time, interleaved
One worker panics mid-runIts done-flag is never written; wrapper times out after 5 s and continues with available results
Stats rollupCorrect — leaf STEP items have hasStats=true, By() children have hasStats=false
API key securityNever stored in state.json — each worker re-reads from reportportal.properties
💡
-p cannot break By() log routing.

By() log routing happens entirely within one worker's single spec execution. ReportAfterEach receives a SpecReport containing only the events for the one spec that just finished — TimelineLocation.Order values are scoped per It block. Each worker has its own completely independent SpecReport in its own memory; there is no shared state between workers for routing.

14 Integrating into Your Own Project

Step-by-step guide to adding ReportPortal reporting to any existing Ginkgo test suite — from zero to a live launch in under 10 minutes.

Prerequisites

🐹

Go 1.21+

Any Go module with Ginkgo v2 tests already written. No changes to individual test files required.

🧪

Ginkgo v2

Your suite must use RunSpecs(t, "Name"). The agent hooks into Ginkgo's reporter interface — not your test code.

📊

ReportPortal v5

A running RP instance (cloud or self-hosted). You need a project slug and an API key from your profile page.

Step 1 — Add the dependency

go get github.com/reportportal/agent-go-ginkgo@latest

Step 2 — Add the blank import to your suite file

Find your *_suite_test.go (the file with RunSpecs). Add one import line — nothing else changes:

package mypackage_test

import (
    "testing"

    . "github.com/onsi/ginkgo/v2"
    . "github.com/onsi/gomega"
    _ "github.com/reportportal/agent-go-ginkgo/pkg/rpagent"  // ← add this
)

func TestMySuite(t *testing.T) {
    RegisterFailHandler(Fail)
    RunSpecs(t, "My Suite Name")  // ← this name appears in RP
}
💡
Multiple suites? Add the blank import to every *_suite_test.go in every package directory. Then run with ginkgo-rp -r — all suites appear under one launch.

Step 3 — Create reportportal.properties

Place this file in your project root (same directory where you run ginkgo-rp):

rp.endpoint = https://your-reportportal-host
rp.api.key  = your_api_key_here
rp.project  = your_project_slug
rp.launch   = MY_SERVICE_TESTS

# Optional
rp.debug    = false
⚠️
Add reportportal.properties to .gitignore — it contains your API key. In CI, use environment variable substitution or a secrets manager to inject the key.

Step 4 — Install ginkgo-rp

go install github.com/reportportal/agent-go-ginkgo/cmd/ginkgo-rp@latest

Step 5 — Run

Single suite — run from inside the package directory, or pass the path:

# from inside the suite directory
cd my-suite/ && ginkgo-rp

# or pass the path from the project root
ginkgo-rp calculator/

Multiple suites — list them explicitly, or use -r to scan recursively:

# specific suites — flags must come before package paths
ginkgo-rp --keep-going calculator/ order-management/

# all suites recursively
ginkgo-rp -r --keep-going

# all suites in parallel
ginkgo-rp -r -p --keep-going

# recursive with focus filter — only matching It() descriptions run
ginkgo-rp -r --keep-going --focus "payment"
ℹ️
--focus matches It() descriptions, not suite names. It does a substring match against every test case name across all suites. Non-matching specs are skipped, not excluded — they still appear in RP with status Skipped, and the total count includes them. Only the matched specs actually run and report Passed or Failed.
⚠️
Always pass --keep-going when running multiple suites.
Without it, Ginkgo stops the entire run as soon as any suite fails — the remaining suites never execute, so their results are never reported to ReportPortal. The launch ends with an incomplete picture.

With --keep-going, all suites run regardless of failures. ReportPortal receives results for every suite, and the launch is finalized with accurate totals.

At the end of the run, ginkgo-rp prints a summary line. With rp.debug = true it also prints a direct link to the launch:

# always printed:
SUCCESS: launch 25db92f6-4a1b-... finalized (10 total tests)

# only when rp.debug = true:
  → https://your-rp-host/ui/#my_project/launches/all/42

The link uses the sequential launch number (e.g. 42) returned by RP when the launch is finished — not the UUID.

Optional — Use priority, reference, and log APIs

These are the only three functions you ever call in test code. Import the package non-blank to use them:

import (
    . "github.com/onsi/ginkgo/v2"
    rpagent "github.com/reportportal/agent-go-ginkgo/pkg/rpagent"
)

var _ = Describe("Payment service", func() {
    It("processes refund",
        Label(rpagent.Priority(0), rpagent.TestReference("PAY-TC-042")),
        func() {
            rpagent.Log("INFO", "initiating refund for order #12345")
            // your test logic
            rpagent.AddAttachment("response.json", "API response")
        })
})

🚀

Launches list

One launch per ginkgo-rp run. Shows total / passed / failed / skipped counts. Each CI run creates a new numbered launch.

🗂

Suite → Describe → It hierarchy

Mirrors your test file structure exactly. Nested Context blocks appear as child items. Drill down to any individual spec.

📋

Logs and attachments

Every rpagent.Log() call appears inline on the test item. Attachments (screenshots, JSON, CSV) are downloadable from the item detail view.

🤖

ML Auto-Analyzer

After enough runs, RP's analyzer learns your failure patterns and suggests defect types automatically — no manual triage for known failures.

ℹ️
No changes to existing tests. The blank import is the only required change to your test code. Priority labels, reference IDs, logs, and attachments are all additive — add them to any test at any time without affecting the others.
